# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A small double-entry accounting application with three parts: `db/` (PostgreSQL schema), `api/` (Go REST API, containerized), and `tui/` (Go terminal UI using Bubble Tea, run on the host). `api` and `tui` are separate Go modules tied together at the root by `go.work`.

## Commands

```sh
make up          # start postgres + containerized api via docker compose (builds api image, loads db/schema.sql)
make down        # stop everything
make tui-run     # run the TUI on the host (talks to http://localhost:30730 by default; MONEY_API_URL overrides)

make db-up       # start only postgres (for iterating on the api locally)
make api-run     # run the api with `go run` against DATABASE_URL / ADDR env vars, instead of the container
make db-shell    # psql into the database (DATABASE_URL defaults to localhost:30731)
make db-reset    # docker compose down -v + db-up (wipes postgres data volume)

make build       # go build both api and tui into ./bin
make test        # go test ./... in both api and tui modules
```

To run a single test: `cd api && go test ./internal/store/... -run TestName` (same pattern under `tui/`).

The `api` module's tests (`internal/store`, `internal/api`, `internal/db`) hit a real PostgreSQL server — `make db-up` is enough — because part of the double-entry invariant lives in a database trigger a mock can't reproduce. Each test creates and drops its own disposable `money_test_*` database via `internal/testutil`, so they never touch the dev database; they skip automatically if no server is reachable. The `tui` module's tests need no database or terminal: `internal/client` is tested against an `httptest` server, and `internal/ui`'s Bubble Tea models are driven directly with synthetic `tea.Msg`/`tea.KeyPressMsg` values (see `keyPress`/`typeString` helpers in `internal/ui/accounts_test.go`) against the same kind of fake server.

Both `api` and `postgres` containers publish ports to `127.0.0.1` only (api on 30730, postgres on 30731) — not reachable from other machines by default. Keep this binding when editing `docker-compose.yml`.

## Architecture

**Monetary amounts** are always integers in the currency's minor unit (e.g. cents), never floats, to avoid rounding errors — but this is an internal-storage/domain-model rule, not the API's wire format (see below). Every `transaction_entries` row is `(account_id, amount, currency_id)`; a currency (`currencies` table, `api/internal/models.Currency`) defines both an amount's meaning (`decimal_places`, how many of the integer's low digits are fractional) and how to render it (`symbol_before`, `symbol_space`, `thousands_separator`, `decimal_separator`), plus an optional `isin`. This "no floats" rule is specifically about ledger amounts — **currency prices** (`currency_prices` table, `api/internal/models.CurrencyPrice`, one exchange-rate observation between two currencies at an instant) deliberately use `DOUBLE PRECISION`/`float64` for `rate`, since it's an approximate market price with no natural tie to either currency's `decimal_places`, not a ledger quantity.

**The API's JSON wire format represents amounts as decimal numbers, not integer minor units** — e.g. `"amount": 10.50`, not `"amount": 1050` — even though `api/internal/models` (the pure domain types: `Entry`, `LedgerEntry`, `CurrencyAmount`, `Transaction`, `Account`) and the store/db layer beneath them stay plain `int64`, entirely unaware of this. The conversion lives in a separate, unexported DTO layer in `api/internal/api/amount.go`: `decimalToMinor`/`minorToDecimal` convert between a `json.Number` (the wire type used for every amount/balance field) and `int64` minor units, given a currency's `decimal_places`, via exact decimal digit-string manipulation — never through `float64` — so there's no rounding error regardless of magnitude; `minorToDecimal` always shows exactly `decimal_places` decimal digits, so a stored `1050` renders as `10.50` and `1000` as `10.00` — matching conventional money notation (`10.50 EUR`, not `10.5 EUR`) rather than trimming trailing zeros. `json.Number` (stdlib `encoding/json`'s `type Number string`) is used as a plain struct field type specifically because it preserves a JSON number's literal text on both marshal and unmarshal without going through `float64` — this works directly on a typed field, unlike `Decoder.UseNumber()` which only affects `interface{}` targets. `amount.go`'s `toEntryJSON`/`toTransactionJSON`/`toAccountJSON`/`toLedgerEntriesJSON` (and their `from*`/slice-mapping counterparts) are the request/response DTOs each handler in `accounts.go`/`transactions.go` converts through; each handler builds the `decimal_places` map it needs via `Handler.currencyDecimalPlaces(ctx)` (one `Currencies.List` call per request), and `fromEntryJSON` returns a 400 for either an unknown `currency_id` or an amount with more decimal digits than that currency's `decimal_places` allows — an amount with *fewer* decimal digits (or none) than `decimal_places` is accepted on input and simply treated as zero-padded, since only the response side fixes the digit count. Any future amount-bearing field added to a handler's response must go through this same DTO layer rather than serializing a `models` type directly, or it will leak raw integer minor units onto the wire.

The TUI mirrors this exactly in `tui/internal/client`: `client.Entry.Amount`, `client.LedgerEntry.Amount`/`Balance`, and `client.CurrencyAmount.Amount` are `json.Number` (the wire type, currency-agnostic — decoding/encoding them needs no currency lookup), and `client.Currency.ToMinorUnits`/`FromMinorUnits` mirror `decimalToMinor`/`minorToDecimal` exactly (including always showing every decimal digit) for converting them to/from `int64` when a currency is in scope. This is a *different* need from `client.Currency.ParseAmount(userText string) (int64, error)`, which parses text a person types into a TUI form using that currency's own display conventions (`thousands_separator`/`decimal_separator`, e.g. `"1.234,56"` for EUR-style input) directly into `int64` minor units — used by both transaction-creation entry points (the ledger's `n`-key quick-entry form in `accounts.go`, and the Transactions tab's general wizard in `transactions.go`). All currency-aware conversion happens at UI-layer call sites, which already hold a `currencyByID`/`currencyIndex` map; the low-level `client` package itself needs none. `transactions.go`'s wizard tracks in-progress entries as `pendingEntry` (a local type distinct from `client.Entry`, holding an exact `int64` amount) precisely so its running per-currency sum-check stays exact while the user is still adding entries, converting to `client.Entry` (wire `json.Number`) only once, at final submission. `currencies.go` splits `formatAmount(wireAmount json.Number, ...)` (for amounts freshly received from the API) from `formatMinorAmount(amount int64, ...)` (for amounts already known to be exact `int64` minor units locally, e.g. a `pendingEntry` or a locally-computed sum) — pick whichever matches what you already have in hand rather than round-tripping through the wire format unnecessarily.

**The double-entry invariant** — a transaction's entries must sum to zero **within each currency** (amounts in different currencies are never summed together; a transaction may freely mix currencies as long as each one balances on its own) — is enforced in two independent places, and both must be kept in sync if this logic ever changes:
1. `api/internal/store/transactions.go`'s `entriesBalance` (called from `TransactionStore.Create`, which returns `store.ErrUnbalanced`, mapped to HTTP 400, if it returns false) sums entries per `currency_id` before writing.
2. `db/schema.sql` has a deferred constraint trigger (`check_transaction_balance`) that re-validates the same rule, per currency, at the database level after any write to `transaction_entries`, as a safety net against any other writer.

There's one deliberate exception to "sum to zero": a transaction touching **exactly two currencies**, each with a nonzero net amount of **opposite sign** (e.g. -10 USD / +8.50 EUR posted to the same or different accounts), is accepted too — both `entriesBalance` and `check_transaction_balance` special-case this shape (`len(nonzero) == 2` with differing signs in Go; `array_length(nonzero_sums, 1) = 2 AND sign(nonzero_sums[1]) <> sign(nonzero_sums[2])` in SQL, over only the currencies whose sum isn't already zero) rather than rejecting it as unbalanced. It represents someone exchanging one currency for another without a separate clearing/equity account, and `db/schema.sql`'s `transaction_implied_prices` view (see below) turns it into a currency-price observation.

**API layering** (`api/`): `cmd/api/main.go` wires config → db pool → store → router → http.Server. `internal/config` reads env vars (`DATABASE_URL`, `ADDR`). `internal/db` sets up the pgx connection pool. `internal/store` is the only package that talks to Postgres (`AccountStore`, `TransactionStore`, `CurrencyStore`, `CurrencyPriceStore` under one `Store`); it defines `ErrNotFound` / `ErrUnbalanced` / `ErrCycle` / `ErrNoRate` which the `internal/api` handlers translate into HTTP status codes. `internal/api/router.go` wires `net/http` 1.22+ method+path patterns (e.g. `"GET /accounts/{id}"`) directly to handler methods — no external router library; a literal segment (e.g. `"GET /currency-prices/rate"`) takes precedence over a same-position wildcard (`"GET /currency-prices/{id}"`) automatically, per Go's own ServeMux precedence rules, so registration order between the two doesn't matter. `internal/api/json.go`'s `pgConstraintMessage` maps a Postgres constraint-violation error to a human-readable message by its constraint name (e.g. `accounts_code_unique`), with generic per-error-code fallbacks for anything unrecognized — extend its switch when adding a new named constraint that should get its own message.

**Currency prices** (`currency_prices` table, `api/internal/store/currency_prices.go`'s `CurrencyPriceStore`) record exchange-rate observations rather than storing a single current rate per currency pair, so a rate can be looked up for any past (or interpolated) instant, not just "now". `RateAt(ctx, baseID, quoteID, at)` answers "how many units of quote was one unit of base worth at `at`" (behind `GET /currency-prices/rate`) without requiring an observation recorded at exactly that instant: `interpolateRate` linearly interpolates between the nearest observations before/after `at` for a given currency pair (using whichever single one exists if only one side has data), and if there's no observation directly relating the two requested currencies, `RateAt` breadth-first searches the graph of currencies connected by any observation (`pairRateSeries` inverts a row's `rate` when the currency being priced is that row's quote side, since an observation only ever records one direction), multiplying each hop's own interpolated rate along the shortest chain that connects them — the way cross-rates normally compose (e.g. EUR/USD × USD/GBP = EUR/GBP). Returns `store.ErrNoRate` (HTTP 404) if the two currencies aren't connected by any chain of observations.

**Transaction-implied currency prices**: a two-currency exchange transaction (see the double-entry invariant's exception, above) is also an exchange-rate observation, but it isn't inserted as a `currency_prices` row — the user explicitly didn't want a copy that would need to be kept in sync by hand if the transaction changed. Instead, `db/schema.sql`'s `transaction_implied_prices` VIEW derives it live from `transaction_entries` every time it's queried: for each qualifying transaction, it converts both currencies' minor-unit net amounts to real units (dividing by `10^decimal_places`, via `currencies.decimal_places`) and computes `base_currency_id` = the currency with the negative net (the one "given up"), `quote_currency_id` = the one with the positive net (the one "received"), `rate` = quote amount ÷ base amount, `as_of` = the transaction's own `timestamp` — so editing or deleting the transaction is reflected immediately, with nothing to keep in sync. `api/internal/store/currency_prices.go`'s `currencyPriceUnionSQL` is a `UNION ALL` of `currency_prices`'s own rows with this view (adding `NULL`/the row's real `transaction_id` respectively to give both sides a `transaction_id` column), used by both `List` and `pricesForCurrency` (and so `RateAt`, transparently) in place of querying `currency_prices` alone — `Get`/`Create`/`Delete` deliberately don't, since a derived observation isn't a stored row and can't be fetched/edited/deleted directly, only via the transaction it comes from. `models.CurrencyPrice.TransactionID` (JSON `transaction_id`, `omitempty`) is `nil` for a real stored row (whose `ID` is that row's actual `currency_prices.id`); for a derived one, `TransactionID` is the transaction's ID and `ID` is always `0` (never a real row, so there's no ID to give it) — API/TUI consumers must check `TransactionID` to tell the two apart, not assume `ID` alone identifies a stored row.

**No migrations**: `db/schema.sql` is the entire schema, applied once via Postgres's docker-entrypoint-initdb.d mechanism (or manually with `psql -f`) to an *empty* database — there's no ALTER-based upgrade path. A schema change means starting from a fresh database (`make db-reset`, or `docker compose down -v` for the full stack), not upgrading one in place.

**TUI** (`tui/`): a single Bubble Tea program (`internal/ui/app.go`) with `Tab`/`Shift+Tab`-cycled Accounts/Transactions/Currencies views (`tab`/`numTabs`/`tabLabels` in `app.go` — generalize these, not a hardcoded 2-way toggle, when adding a fourth). There's no separate row naming the tabs — `View()`'s title line itself is `"Money — " + tabLabels[m.active]`, the only place the active tab is named — so switching tabs is discoverable only via the footer's `"tab: switch view"` hint, not a visible list of the other tabs. `App.title` overrides that default while viewing an account's ledger (`accountsModeLedger`/`accountsModeLedgerCreate`): the title instead reads `"Money — Transactions in "` plus `accountBreadcrumb`'s `" → "`-joined path from that account's outermost ancestor down to itself (e.g. `"Assets → Cash → Juan"`, walking up `ParentID` through `accountsModel.rows`) — the ledger view itself (`accountsModel.View`) has no subtitle of its own naming the account, so this is the only place it's shown. Backed by `internal/client` — a plain REST client for the API (no shared code with `api/`; it's a separate consumer of the public HTTP contract). Bubble Tea reports terminal bracketed-paste input as its own `tea.PasteMsg`, distinct from `tea.KeyMsg` (regular typing) even though bubbles' `textinput.Model.Update` already handles both identically once a message reaches it — so every place that special-cases `tea.KeyMsg` to route into a mode's own key-command dispatch (`App.Update`, and each tab's own top-level `Update`) has a parallel `case tea.PasteMsg:` routing it the same way, but *only* to whichever mode(s) actually have a focused text field (e.g. `accountsModeCreate`/`accountsModeLedgerCreate`, not `accountsModeList`/`accountsModeConfirmDelete`) — `App`'s case reuses `updateActiveTab` (also used by `tea.KeyMsg`) so a paste can never reach a tab that isn't visible. The `updateCreate`/`updateLedgerCreate` functions themselves take `tea.Msg` rather than `tea.KeyMsg` for the same reason, narrowing to a key only where they actually dispatch a key command (e.g. via `if key, ok := msg.(tea.KeyMsg); ok { switch key.String() { ... } }`) and falling through unconditionally to forward whatever `msg` is to the focused field/picker's own `Update` — never calling `msg.String()` on an unnarrowed `tea.Msg`, since `tea.PasteMsg` has its own `String()` (returning the pasted content itself), which could otherwise spuriously match a key command by coincidence. The "new account" and "new currency" forms are pop-ups composited on top of their list (rather than replacing it) via `overlayCentered` in `tui/internal/ui/styles.go`, which uses lipgloss v2's `Layer`/`Compositor` — the general mechanism for any future modal/overlay in the TUI. Editing (`e`, Accounts and Currencies only — Transactions has no edit) reuses that same pop-up rather than a separate one: `startEdit` on each model pre-fills it from the selected record and sets `editingID` to that record's ID, and `submitForm` (shared by both create and edit) branches on whether `editingID` is nil to POST or PUT; the same pattern should be followed for any future editable tab rather than building a distinct edit form. `client.Currency.Format` (in `tui/internal/client/models.go`) renders an amount per that currency's own rules; `tui/internal/ui/currencies.go`'s `currencyByID`/`indexCurrencies`/`formatAmount` let the Accounts and Transactions tabs render amounts without needing to track currencies' formatting rules themselves. The currencies list and its "new currency" form don't expose `symbol_before`/`symbol_space`/`thousands_separator`/`decimal_separator`/`decimal_places` individually — instead they show/take a single `Format` example of how the currency renders a fixed test quantity of 1234 whole units (e.g. `"$1,234.00"`, `"1.234,00 EUR"`); `currencies.go`'s `parseCurrencyFormat`/`parseFormatNumber` derive those five fields back out of such a string (relying on 1234's fixed four digits to unambiguously tell a thousands separator from a decimal one), and `exampleAmount` is the inverse, used to render the list's Format column from a currency's actual stored rules — each of the three tab models independently loads its own copy of the currency list (via the shared `currenciesLoadedMsg` type, so one tab's load also refreshes the other two's cache through the same App-level message broadcast used for all non-key messages) rather than sharing one cache, matching the app's existing "independent per-tab models" style.

**Accounts** support a self-referencing `parent_id` for a chart-of-accounts hierarchy; deletes are `ON DELETE RESTRICT` (children/entries block deleting a parent/account). `AccountStore.Update` rejects (`store.ErrCycle`, HTTP 400) a `parent_id` that would make the account its own ancestor — itself directly, or transitively through some chain of parents — via `wouldCreateCycle`, which walks up the existing `parent_id` chain from the proposed parent looking for the account's own ID; the TUI's edit form also excludes the account and all its descendants from its own Parent dropdown (`accountsExcludingSubtree`) so the invalid choice isn't offered in the first place, but the store-level check is what actually guarantees the invariant. An account's `balances` are never stored — `AccountStore.attachBalances` (used by `List`/`Get`) computes them on every read via a `GROUP BY account_id, currency_id` query, and it's always just that account's own entries, with no roll-up from children; an account with no entries in a currency has no entry for it at all (not a zero one). `AccountStore.attachLastTransactionAt` (also used by `List`/`Get`, and following the same own-entries-only convention as `attachBalances`) similarly computes each account's `last_transaction_at` — the most recent transaction's timestamp among its own entries, `nil`/omitted for an account with none — via a `MAX(t.timestamp) ... GROUP BY te.account_id` query rather than storing it. `AccountStore.Ledger` (behind `GET /accounts/{id}/transactions`) similarly computes a running balance **per currency** via a SQL window function partitioned by `currency_id` (`SUM(...) OVER (PARTITION BY currency_id ORDER BY timestamp, id)`), rather than the TUI or any Go code summing it; a transaction posting to an account in more than one currency contributes one ledger row per currency. The TUI's ledger table (`ledgerTable` in `accounts.go`) sizes its own columns dynamically rather than using one fixed layout: `ledgerAmountColumnWidths` measures the widest formatted Value and the widest formatted Balance actually present among the currently-loaded entries (floored at each column header's own width), and `ledgerColumns` gives Description whatever width is left of the terminal once Timestamp and those two are accounted for (floored at `ledgerMinDescriptionWidth`) — so typical short amounts (most currencies) don't reserve far more space than they need the way a single generous fixed width would, and a wide terminal gives Description most of the extra room instead of it going to waste. `syncLedgerTable` recomputes both columns and rows together (`SetColumns`+`SetRows`, since row content must right-align to the same freshly-measured widths — see `rightAlign`) and must be called after *any* of the three things its calculation depends on changes: the terminal width (`SetSize`), the loaded entries (`ledgerLoadedMsg`), or the currencies used to format them (`currenciesLoadedMsg`) — a call site that mutates one of those without also calling it will show stale, wrongly-sized columns. Each account also has a `position`, ordering it for display among its siblings (others sharing the same `parent_id`, `NULL` included) — `AccountStore.Create` assigns it automatically (one past its highest-positioned sibling, via a `MAX(position)+1` subquery keyed on `parent_id IS NOT DISTINCT FROM $1` to handle the `NULL` case), `AccountStore.Update` deliberately never touches it, and `AccountStore.Move` (behind `POST /accounts/{id}/move`, body `{"direction": "up"|"down"}`) is the only way it changes after that — swapping it with the adjacent sibling's, in one transaction, or silently no-oping at either end of the sibling list. The TUI's accounts list renders the hierarchy as a tree drawn with connector lines (`orderAccountsAsTree` in `tui/internal/ui/accounts.go`): each account immediately followed by its children, siblings at every level ordered by `Position` (ID only breaks a tie). `orderAccountsAsTree`'s depth-first walk computes each node's `accountTreeNode.prefix` — `"├── "`/`"└── "` before a non-root account's own name (the latter iff it's the last of its siblings), preceded by whatever `"│   "`/`"    "` run its ancestors' own last-ness inherited down (empty at depth 0, since multiple root accounts are laid out as an unconnected forest, each starting its own tree, rather than one implicit shared root) — and `nodesToRows` uses that prefix directly rather than indenting by `depth`; a multi-currency `Balances` cell is joined into one comma-separated string per account (`formatBalances`), since bubbles' table has no multi-line-cell concept; a "Last transaction" column (`formatLastTransactionAt`) renders `LastTransactionAt` the same way the ledger table's own Timestamp column does (converted to local time via `timestampLayout`), blank for an account with none; pressing `Enter` on a row drills into that account's ledger view, and `K`/`J` (plain capital letters, not `Shift`+arrow — some terminals, e.g. xfce4-terminal, don't report that combination as a distinguishable event) call `client.MoveAccount` and reload, using `accountsModel.selectAfterReload` to keep the cursor on the account that moved rather than the fixed row index. Neither the list nor the "new account" form's Parent dropdown ever shows an account's ID — just its name — since `selectedParentID`/`parentCursorFor` map a dropdown row to an account by position in `accountsModel.parentOptions` (an `[]accountTreeNode`, built with the same `orderAccountsAsTree` the list uses) rather than by any ID shown on screen; unlike the list, `parentDropdownRows` deliberately ignores `prefix` and indents by `depth` instead (`strings.Repeat("  ", depth)`) — connector lines suit surveying the whole hierarchy's shape, but read as clutter in a picker meant just for choosing one account.

**The ledger's "new entry" form** (`n` inside `accountsModeLedger`, see `startLedgerEntry`/`ledgerEntryPopup` in `accounts.go`) is a second, distinct way to create a transaction, deliberately separate from the Transactions tab's own multi-entry wizard (`transactionsModel`'s `updateCreate`/`submitCreate` in `transactions.go`) rather than sharing its state machine — it only ever produces a two-entry transaction between the account whose ledger is open and one other, so it doesn't need that wizard's repeat-until-done loop. Unlike that wizard (a full-content replacement, matching its own step-by-step nature), this form is a `createPopup`-style table-shaped pop-up composited over the ledger view (wired into `App.View`'s overlay switch in `app.go` alongside `accountsModeCreate`/`currenciesModeCreate`) — two rows, Timestamp/Description/Amount/Currency for this account above Account/Amount/Currency for the other side. Like the account/currency forms, `Tab`/`Shift+Tab` are the only way to move between its seven fields; both Currency fields and Other account are pickers (`ledgerCurrencyPicker`/`ledgerOtherCurrencyPicker`/`ledgerAccountPicker`) that behave like the account form's Parent field — dropdown shown while focused (header stripped via the shared `stripPickerHeader` in `styles.go`, also used by `createPopup`), current selection shown as plain text once focus moves on. Because a picker isn't always in the row's first column (both Currency fields are the last of four/three), its dropdown is indented under its own header via `indentLines`/`fieldPickerOffset` rather than sitting flush against the pop-up's left edge (only correct for a first-column picker, e.g. Other account or `createPopup`'s Parent). And because this form has three pickers rather than `createPopup`'s one, each dropdown's row reserves a constant footprint via `pickerSlot` (`ledgerPickerHeight`, and `ledgerRow1PickerSlotWidth`/`ledgerRow2PickerSlotWidth` for its row's own width) whether or not it's currently showing — otherwise the pop-up's own size, and so its centered position, would visibly grow and shrink as focus moved on and off each picker in turn. The two Currency pickers are narrower than Other account's (`ledgerCurrencyPickerWidth`, matching just the Currency field's own column, vs `parentPickerWidth` sized for potentially-long account names) — coincidentally both row 2 slot widths still work out equal (`fieldPickerOffset(0)+parentPickerWidth == fieldPickerOffset(2)+ledgerCurrencyPickerWidth`), so `ledgerRow2PickerSlotWidth` covers both Other account and row 2's Currency picker without needing a wider reservation for either. Both currency pickers default to whichever currency this account's ledger was last posted in (`lastUsedCurrencyID`, falling back to the first available currency), though the second row's can be changed independently — the two entries need not share a currency. The second row's amount defaults to the negation of the first only when both rows' currencies match (the one case where that's an unambiguous default, since no exchange rate is applied here); otherwise it's required, and either way the API's own zero-sum-per-currency check is what actually decides whether the pair balances, exactly as for the general wizard. The "other account" dropdown (`accountsOtherThan`) excludes only the account whose ledger is open — unlike the account form's Parent dropdown, it does *not* exclude that account's descendants, since posting between an account and its own child is a perfectly ordinary transaction, not a hierarchy cycle.
