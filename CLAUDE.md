# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A small double-entry accounting application with three parts: `db/` (PostgreSQL schema), `api/` (Go REST API, containerized), and `tui/` (Go terminal UI using Bubble Tea, run on the host). `api` and `tui` are separate Go modules tied together at the root by `go.work`.

## Commands

```sh
make up          # start postgres + containerized api via docker compose (builds api image, loads db/schema.sql)
make down        # stop everything
make tui-run     # run the TUI on the host (talks to http://localhost:30730 by default; MONEY_API_URL overrides)

make db-up       # start only postgres (for iterating on the api locally)
make api-run     # run the api with `go run` against DATABASE_URL / ADDR env vars, instead of the container
make db-shell    # psql into the database (DATABASE_URL defaults to localhost:30731)
make db-reset    # docker compose down -v + db-up (wipes postgres data volume)

make build       # go build both api and tui into ./bin
make test        # go test ./... in both api and tui modules
```

To run a single test: `cd api && go test ./internal/store/... -run TestName` (same pattern under `tui/`).

The `api` module's tests (`internal/store`, `internal/api`, `internal/db`) hit a real PostgreSQL server — `make db-up` is enough — because part of the double-entry invariant lives in a database trigger a mock can't reproduce. Each test creates and drops its own disposable `money_test_*` database via `internal/testutil`, so they never touch the dev database; they skip automatically if no server is reachable. The `tui` module's tests need no database or terminal: `internal/client` is tested against an `httptest` server, and `internal/ui`'s Bubble Tea models are driven directly with synthetic `tea.Msg`/`tea.KeyPressMsg` values (see `keyPress`/`typeString` helpers in `internal/ui/accounts_test.go`) against the same kind of fake server.

Both `api` and `postgres` containers publish ports to `127.0.0.1` only (api on 30730, postgres on 30731) — not reachable from other machines by default. Keep this binding when editing `docker-compose.yml`.

## Architecture

**Monetary amounts** are always integers in the currency's minor unit (e.g. cents), never floats, to avoid rounding errors. Every `transaction_entries` row is `(account_id, amount, currency_id)`; a currency (`currencies` table, `api/internal/models.Currency`) defines both an amount's meaning (`decimal_places`, how many of the integer's low digits are fractional) and how to render it (`symbol_before`, `symbol_space`, `thousands_separator`, `decimal_separator`), plus an optional `isin`.

**The double-entry invariant** — a transaction's entries must sum to zero **within each currency** (amounts in different currencies are never summed together; a transaction may freely mix currencies as long as each one balances on its own) — is enforced in two independent places, and both must be kept in sync if this logic ever changes:
1. `api/internal/store/transactions.go`'s `TransactionStore.Create` sums entries per `currency_id` before writing and returns `store.ErrUnbalanced` (mapped to HTTP 400) if any currency's sum isn't zero.
2. `db/schema.sql` has a deferred constraint trigger (`check_transaction_balance`) that re-validates the same invariant, per currency, at the database level after any write to `transaction_entries`, as a safety net against any other writer.

**API layering** (`api/`): `cmd/api/main.go` wires config → db pool → store → router → http.Server. `internal/config` reads env vars (`DATABASE_URL`, `ADDR`). `internal/db` sets up the pgx connection pool. `internal/store` is the only package that talks to Postgres (`AccountStore`, `TransactionStore`, `CurrencyStore` under one `Store`); it defines `ErrNotFound` / `ErrUnbalanced` which the `internal/api` handlers translate into HTTP status codes. `internal/api/router.go` wires `net/http` 1.22+ method+path patterns (e.g. `"GET /accounts/{id}"`) directly to handler methods — no external router library. `internal/api/json.go`'s `pgConstraintMessage` maps a Postgres constraint-violation error to a human-readable message by its constraint name (e.g. `accounts_code_unique`), with generic per-error-code fallbacks for anything unrecognized — extend its switch when adding a new named constraint that should get its own message.

**No migrations**: `db/schema.sql` is the entire schema, applied once via Postgres's docker-entrypoint-initdb.d mechanism (or manually with `psql -f`) to an *empty* database — there's no ALTER-based upgrade path. A schema change means starting from a fresh database (`make db-reset`, or `docker compose down -v` for the full stack), not upgrading one in place.

**TUI** (`tui/`): a single Bubble Tea program (`internal/ui/app.go`) with `Tab`/`Shift+Tab`-cycled Accounts/Transactions/Currencies views (`tab`/`numTabs`/`tabLabels` in `app.go` — generalize these, not a hardcoded 2-way toggle, when adding a fourth), backed by `internal/client` — a plain REST client for the API (no shared code with `api/`; it's a separate consumer of the public HTTP contract). The "new account" and "new currency" forms are pop-ups composited on top of their list (rather than replacing it) via `overlayCentered` in `tui/internal/ui/styles.go`, which uses lipgloss v2's `Layer`/`Compositor` — the general mechanism for any future modal/overlay in the TUI. Editing (`e`, Accounts and Currencies only — Transactions has no edit) reuses that same pop-up rather than a separate one: `startEdit` on each model pre-fills it from the selected record and sets `editingID` to that record's ID, and `submitForm` (shared by both create and edit) branches on whether `editingID` is nil to POST or PUT; the same pattern should be followed for any future editable tab rather than building a distinct edit form. `client.Currency.Format` (in `tui/internal/client/models.go`) renders an amount per that currency's own rules; `tui/internal/ui/currencies.go`'s `currencyByID`/`indexCurrencies`/`formatAmount` let the Accounts and Transactions tabs render amounts without needing to track currencies' formatting rules themselves. The currencies list and its "new currency" form don't expose `symbol_before`/`symbol_space`/`thousands_separator`/`decimal_separator`/`decimal_places` individually — instead they show/take a single `Format` example of how the currency renders a fixed test quantity of 1234 whole units (e.g. `"$1,234.00"`, `"1.234,00 EUR"`); `currencies.go`'s `parseCurrencyFormat`/`parseFormatNumber` derive those five fields back out of such a string (relying on 1234's fixed four digits to unambiguously tell a thousands separator from a decimal one), and `exampleAmount` is the inverse, used to render the list's Format column from a currency's actual stored rules — each of the three tab models independently loads its own copy of the currency list (via the shared `currenciesLoadedMsg` type, so one tab's load also refreshes the other two's cache through the same App-level message broadcast used for all non-key messages) rather than sharing one cache, matching the app's existing "independent per-tab models" style.

**Accounts** support a self-referencing `parent_id` for a chart-of-accounts hierarchy; deletes are `ON DELETE RESTRICT` (children/entries block deleting a parent/account). An account's `balances` are never stored — `AccountStore.attachBalances` (used by `List`/`Get`) computes them on every read via a `GROUP BY account_id, currency_id` query, and it's always just that account's own entries, with no roll-up from children; an account with no entries in a currency has no entry for it at all (not a zero one). `AccountStore.Ledger` (behind `GET /accounts/{id}/transactions`) similarly computes a running balance **per currency** via a SQL window function partitioned by `currency_id` (`SUM(...) OVER (PARTITION BY currency_id ORDER BY timestamp, id)`), rather than the TUI or any Go code summing it; a transaction posting to an account in more than one currency contributes one ledger row per currency. Each account also has a `position`, ordering it for display among its siblings (others sharing the same `parent_id`, `NULL` included) — `AccountStore.Create` assigns it automatically (one past its highest-positioned sibling, via a `MAX(position)+1` subquery keyed on `parent_id IS NOT DISTINCT FROM $1` to handle the `NULL` case), `AccountStore.Update` deliberately never touches it, and `AccountStore.Move` (behind `POST /accounts/{id}/move`, body `{"direction": "up"|"down"}`) is the only way it changes after that — swapping it with the adjacent sibling's, in one transaction, or silently no-oping at either end of the sibling list. The TUI's accounts list renders the hierarchy as an indented tree (`orderAccountsAsTree` in `tui/internal/ui/accounts.go`): each account immediately followed by its children, siblings at every level ordered by `Position` (ID only breaks a tie); a multi-currency `Balances` cell is joined into one comma-separated string per account (`formatBalances`), since bubbles' table has no multi-line-cell concept; pressing `Enter` on a row drills into that account's ledger view, and `Shift+↑`/`Shift+↓` call `client.MoveAccount` and reload, using `accountsModel.selectAfterReload` to keep the cursor on the account that moved rather than the fixed row index.
